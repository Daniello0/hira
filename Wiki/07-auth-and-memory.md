# 07. Аутентификация, чаты и память модели

Статус: черновик · Последнее обновление: 2026-10-03

---

## 1. Аутентификация

### Схема

Пара токенов: короткоживущий access-JWT и долгоживущий refresh-токен с ротацией.

| Параметр | Значение |
|---|---|
| Access-токен | JWT, HS256, TTL 15 мин, передаётся в `Authorization: Bearer` |
| Refresh-токен | Случайные 32 байта, TTL 30 дней, httpOnly + Secure + SameSite=Strict cookie |
| Хранение refresh | В БД хранится только SHA-256 хеш токена |
| Ротация | При каждом `/auth/refresh` старый токен отзывается, выдаётся новый |
| Обнаружение кражи | Использование уже отозванного токена → отзыв всей семьи токенов пользователя |
| Хеширование пароля | argon2id (memory 64 МБ, time 3, parallelism 4) |
| Политика пароля | Минимум 10 символов, проверка по списку скомпрометированных (k-anonymity через HIBP или локальный список) |
| Rate limiting | 5 попыток входа в минуту на IP + на email, затем экспоненциальная задержка |

Payload access-токена минимален: `sub` (userId), `role`, `iat`, `exp`. Никаких email и персональных данных в токене.

### Почему не готовое решение

Auth.js / Clerk / Supabase Auth решили бы задачу быстрее, но:
1. курсовая — про разработку, и собственная реализация авторизации это законный объём работы для главы 3;
2. внешний провайдер тянет зависимость от облака, а требование — локальный PostgreSQL;
3. JWT + ротация refresh — стандартная тема, которую комиссия точно спросит, и лучше её реализовать самому.

Решение фиксируется в [10-decision-log.md](10-decision-log.md).

### Что вне scope

OAuth-вход через Google/GitHub, двухфакторная аутентификация, восстановление пароля по email (требует SMTP-инфраструктуры), **подтверждение email** (Q20 — нет, возможно на диплом). Всё это — в «направления развития».

## 2. Чаты

Модель — как в ChatGPT/Gemini: пользователь ведёт произвольное число независимых чатов.

- **Создание.** Чат создаётся пустым; заголовок генерируется LLM по первому сообщению (`POST /internal/v1/title-chat`), пользователь может переименовать.
- **Изоляция.** Каждый чат — независимый контекст поиска. Уточнение «а можно удалёнку?» действует в пределах своего чата.
- **Архивация вместо удаления** по умолчанию; жёсткое удаление — отдельным действием с подтверждением.
- **Пагинация.** Сообщения грузятся курсором от свежих к старым.
- **Снимок результатов.** Показанные вакансии с объяснениями сохраняются в `message_vacancies`, поэтому старый чат при открытии выглядит ровно так, как в момент разговора, даже если корпус с тех пор изменился.

## 3. Память модели

Это одна из главных новых фич. Реализуется тремя уровнями с разным временем жизни и разной стоимостью.

```
┌──────────────────────────────────────────────────────────┐
│ Уровень 1. Рабочее окно                                  │
│ Последние N сообщений чата дословно                      │
│ Живёт: в пределах чата · Стоимость: токены контекста     │
├──────────────────────────────────────────────────────────┤
│ Уровень 2. Сводка чата                                   │
│ LLM-сжатие вытесненных сообщений в текст сводки          │
│ Живёт: в пределах чата · Обновляется каждые N сообщений  │
├──────────────────────────────────────────────────────────┤
│ Уровень 3. Долговременная память                         │
│ Структурированные факты о пользователе, кросс-чатовые    │
│ Живёт: постоянно · Извлекается семантически по запросу   │
└──────────────────────────────────────────────────────────┘
```

### 3.1 Уровень 1 — рабочее окно

Последние `WORKING_WINDOW_SIZE` (стартово **10**) сообщений передаются в `understand` и `generate` дословно. Простой и дешёвый уровень, обеспечивает связность коротких диалогов.

**Параметры памяти (Q21):** стартовые значения — **константы, подобранные эмпирически** (`WORKING_WINDOW_SIZE=10`, пересборка сводки каждые **8** сообщений, порог confidence **0.7**, top-5 семантических фактов). Точная настройка — на этапе тестирования, не блокирует разработку.

### 3.2 Уровень 2 — сводка чата

Когда число сообщений превышает окно, вытесненная часть сжимается LLM в сводку (`POST /internal/v1/summarize-chat`) и пишется в `chats.summary`. Сводка перегенерируется инкрементально: `новая сводка = f(старая сводка, вытесненные сообщения)`.

Формат сводки фиксированный, не свободный текст — так она не «расползается» с каждой итерацией:

```
Цель поиска: ...
Уточнённые требования: ...
Отвергнутые варианты и почему: ...
Обсуждённые вакансии: ...
```

Блок «отвергнутые варианты» — то, чего обычно нет: он не даёт системе повторно предлагать то, что пользователь уже отклонил.

### 3.3 Уровень 3 — долговременная память

Самая содержательная часть. Хранится в `user_memories` (см. [04-data-model.md](04-data-model.md)).

**Извлечение.** После каждого обмена репликами асинхронно (fire-and-forget, не блокируя ответ) вызывается `POST /internal/v1/extract-memory`. Модель получает последние сообщения и уже существующую память, возвращает кандидатов:

```ts
interface MemoryCandidate {
  kind: MemoryKind;          // PREFERENCE | CONSTRAINT | FACT | GOAL
  content: string;           // «Не рассматривает работу с переездом»
  confidence: number;        // 0..1
  operation: 'ADD' | 'UPDATE' | 'CONTRADICTS';
  targetMemoryId?: string;   // для UPDATE / CONTRADICTS
  sourceMessageId: string;
}
```

**Правила записи:**

- кандидаты с `confidence < 0.7` отбрасываются;
- дубликаты отсекаются по косинусной близости эмбеддинга выше 0.9;
- при `CONTRADICTS` старый факт помечается `revoked_at`, новый записывается — история конфликта сохраняется;
- всё, что записано, немедленно видно пользователю на экране «Память» с указанием сообщения-источника.

**Извлечение при поиске.** В контекст запроса попадает не вся память (это не масштабируется и загрязняет промпт), а:
- все факты с `kind = CONSTRAINT` (ограничения действуют всегда);
- все закреплённые (`is_pinned`);
- top-5 остальных по косинусной близости эмбеддинга памяти к эмбеддингу текущего запроса.

**Устаревание.** Факты типа `GOAL` получают `expires_at` (по умолчанию 90 дней). Память, не подтверждавшаяся долго, понижается в `confidence` при следующем пересчёте.

### 3.4 Выключатель межчатовой памяти

Уровень 3 и есть межчатовая память: факты, а не дословные ленты других чатов. Настройка аккаунта `cross_chat_memory_enabled`, по умолчанию **включена** (ADR-026).

- Включена — в контекст попадают ограничения, закреплённые факты и top-5 по близости, как в §3.3. Новые факты из чата и из вызова пишутся как раньше.
- Выключена — `user_memories` не читаются и не пополняются. Окно сообщений и сводка **текущего** чата (уровни 1–2) работают. Уже записанные факты остаются в базе, пока пользователь их не удалит.
- Флаг реплики `useMemory: false` — отказ на одно сообщение, при включённой настройке аккаунта.
- Библиотека файлов этим выключателем не управляется: резюме и md/txt пользователь положил явно. См. [11-hira.md](11-hira.md).

### 3.5 Что считать памятью, а что профилем

Граница важная и её стоит зафиксировать:

| | Профиль (`user_profiles`, `user_profile_skills`) | Память (`user_memories`) |
|---|---|---|
| Источник | Введено пользователем явно | Извлечено из диалога |
| Структура | Строгая схема, типизированные поля | Свободная формулировка + тип |
| Использование | Жёсткие фильтры и расчёт skill gap | Мягкие предпочтения и контекст промпта |
| Доверие | Высокое | Со значением `confidence` |

Навык, извлечённый из диалога с высокой уверенностью, может быть **предложен** к добавлению в профиль, но не добавляется автоматически — пользователь подтверждает (Q22, ADR-021). Это защита от того, чтобы фраза «я как-то трогал Java на курсе» превратилась в «Java: confident level».

Аналогично для **предпочтений по вакансиям** (формат работы, зарплатный порог, локация): из диалога → предложение → подтверждение → поля профиля.

### 3.6 Парсинг резюме (Q7)

1. Пользователь загружает PDF резюме в библиотеку (экран Library; с профиля — та же загрузка).
2. `core-api` извлекает текст локально, вызывает `llm-service` `/parse-resume`.
3. Modal с кандидатами навыков и опытом; пользователь отмечает галочками.
4. Принятые навыки → `user_profile_skills` с `source=RESUME`.

Файл остаётся документом `RESUME` в библиотеке. Повторный парсинг того же файла — из кэша по hash. DOCX из ADR-016 сужен до PDF (ADR-024): один путь загрузки.

## 4. Приватность

Явный раздел, потому что тема памяти его провоцирует, и на защите вопрос прозвучит:

- пользователь видит **всё**, что о нём сохранено, включая источник каждого факта;
- любой факт можно удалить, всю память можно стереть одной кнопкой;
- межчатовую память можно выключить целиком; для одной реплики остаётся флаг `useMemory: false`;
- при удалении аккаунта каскадно удаляются чаты, память, профиль, избранное, библиотека и транскрипты вызовов;
- в промпт внешней LLM не уходит email, идентификатор пользователя или иные прямые идентификаторы — только содержательные факты;
- пароли — argon2id, refresh-токены — хеши, ключи провайдеров — только в переменных окружения.

### Demo-лимиты (Q17)

| Режим | Лимит |
|---|---|
| Без регистрации | 1 чат, 3 запроса total |
| С регистрацией | чатов сколько угодно, 20 поисковых запросов/день |

Счётчики — Redis; при превышении — `429 RATE_LIMIT_EXCEEDED`.
