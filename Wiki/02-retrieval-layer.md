## 1. Что было в курсовой 2026 и почему этого мало

Пайплайн 2026 года:

```
запрос → LLM извлекает категориальные фильтры (JSON Schema)
       → жёсткая фильтрация по 7 полям + ILIKE по role_keywords
       → релаксация фильтров, если кандидатов мало
       → Sentence-BERT (paraphrase-multilingual-MiniLM-L12-v2, 384d)
       → pgvector, ORDER BY cosine_distance
       → эвристический буст по словарю доменов (+0.03 за совпадение, максимум 3)
       → top-5
```

Это честный bi-encoder RAG. Его конкретные слабые места, подтверждённые аудитом кода:

| Проблема | Последствие |
|---|---|
| `paraphrase-multilingual-MiniLM-L12-v2` — модель 2021 года, обучена на задаче перефразирования, не на retrieval | На MTEB-подобных бенчмарках такие модели проигрывают современным 10–15 пунктов |
| Размерность 384, контекст 512 токенов | Длинные описания вакансий обрезаются |
| Асимметрия пространств: вакансия кодируется взвешенным шаблоном (title × 4, поля × 3), запрос — сырым текстом | Запрос и документ живут в разных «режимах» одного пространства |
| Нет лексической ветви | Точные термины («1С:Предприятие 8.3», «ГОСТ 34», конкретный стек) теряются — классическая слепая зона плотного поиска |
| Нет векторного индекса (HNSW) | Полный скан; на ~1000 строк терпимо, на 50 000 — нет |
| Доменный буст зашит тремя словарями (horeca / it / logistics) | Не масштабируется, не обобщается, выглядит как костыль на защите |
| Нет реранкера | Финальный порядок определяется bi-encoder'ом, который принципиально слабее cross-encoder'а |
| Нет связей между сущностями | Невозможны запросы «куда расти после X», «что близко к моему набору навыков» |
| Объяснение = одно число `cosine_distance` | Пользователь не понимает, почему это ему показали |

## 2. Надо ли брать Graph RAG? Разбор актуальных данных

Предложение «заменить Sentence-BERT на Graph RAG» я проверил по литературе. Вывод короткий: **заменять — нет, добавлять как третью ветвь — да**. Обоснование ниже.

### 2.1 Что говорят замеры

Microsoft GraphRAG (индексация: LLM извлекает сущности и связи, строится взвешенный граф, кластеризация Leiden, предгенерация сводок сообществ) действительно выигрывает — но избирательно:

- Выигрыш в 72–83% сравнений по полноте (comprehensiveness) и 62–82% по разнообразию против vector RAG — **на задачах глобального обобщения корпуса**.
- HippoRAG: Recall@5 растёт с 73.4% (naïve RAG) до 87.8% (graph-guided), до +31 пункта на мультихоп-датасетах MuSiQue и 2Wiki.
- **Но на простом извлечении фактов — ничья**: 60.9 (чанки) против 60.1 (граф). Более того, отдельные работы фиксируют, что GraphRAG проигрывает обычному RAG 13.4% точности на Natural Questions, потому что граф вносит избыточную и шумную информацию для простых запросов.
- Обзор «When to use Graphs in RAG» (arXiv 2506.05690) формулирует это прямо: «basic RAG is comparable to or outperforms GraphRAG in simple fact retrieval tasks».

Сводка: граф выигрывает на сложных рассуждениях (+10 пунктов) и контекстной суммаризации (+13 пунктов), играет вничью на простом поиске фактов, и стоит существенно дороже на индексации.

### 2.2 Что из этого следует для поиска вакансий

Распределение запросов в нашей задаче смешанное:

- «Junior Python разработчик, удалёнка, Минск» — **простой** запрос, тут граф — чистые накладные расходы;
- «хочу работать с данными, но чтобы было связано с медициной» — **сложный**, нужна связь «навык → смежный навык → отрасль»;
- «куда расти после джуна на 1С» — **мультихоп**, без графа переходов между ролями не решается;
- «какие вакансии подходят под мой профиль, но требуют на один навык больше» — **структурный**, это буквально обход графа.

То есть чистый GraphRAG — неверный ответ, и чистый vector RAG — тоже неверный.

### 2.3 Что считается стандартом в 2026

Все независимые обзоры сходятся на одном: **гибридный поиск с маршрутизацией по типу запроса**. Векторная ветвь находит точки входа, лексическая ловит точные термины, графовая достраивает связанный контекст; результаты сливаются ранговой фузией. HippoRAG 2 устроен ровно так: вектор ищет точки входа в граф, обход идёт от них.

Для нашей предметной области это подтверждается двумя свежими работами:

- **JobMatchAI** (ACL 2026, demo track) — продакшн-система подбора: Transformer-эмбеддинги + граф навыков в Neo4j (рёбра `REQUIRES`, `RELATED_TO`, построены из таксономии ESCO v1.1.1 плюс ручной словарь синонимов) + гибридный retrieval BM25 / KG / semantic + «белый ящик» реранкинга — многофакторная функция полезности, разложенная на skill fit, experience, location, salary, semantic similarity, company. nDCG@10 = 0.81.
- **CareerPathKG** (EACL 2026, industry track) — граф карьерных путей: профессии, требуемые навыки, переходы между ролями, на базе стандартизованных таксономий, обогащённых реальными вакансиями. Решает CV-assessment, CV–JD matching и career guidance одним графом.

Обе работы делают то же, что я предлагаю ниже. Это хорошо: значит, решение не выдумано, а воспроизводит признанный подход, и на защите есть на что сослаться.

### 2.4 Итоговое решение

> **Не «Sentence-BERT → GraphRAG», а «Sentence-BERT → гибридный retrieval поверх графа навыков с cross-encoder реранкингом и пофакторной объяснимостью».**

Формулировка для введения курсовой: *предложена и реализована архитектура гибридного поиска вакансий, объединяющая лексическую (BM25), плотную (bi-encoder) и графовую (обход графа навыков) ветви извлечения с ранговой фузией, переранжированием cross-encoder-моделью и пофакторным объяснением релевантности.*

### S0. Понимание запроса

Вызов `llm-service POST /understand` со structured output. На выходе:

```ts
interface SearchIntent {
  rewrittenQuery: string;        // самодостаточный запрос с раскрытыми кореференциями
  role: string | null;           // нормализованное название роли
  skills: SkillMention[];        // { surface, canonicalId, required: boolean }
  seniority: SeniorityLevel | null;
  hardConstraints: {             // нарушать нельзя
    workFormat?: WorkFormat[];
    employment?: EmploymentType[];
    location?: string[];
    salaryMin?: number;
  };
  softConstraints: Record<string, number>;  // предпочтения с весами 0..1
  complexity: QueryComplexity;   // SIMPLE | MODERATE | COMPLEX | EXPLORATORY
  intentType: IntentType;        // SEARCH | REFINE | COMPARE | CAREER_ADVICE | SMALL_TALK
}
```

Два отличия от 2026 года. Первое: запрос **переписывается** с учётом истории — «а можно удалёнку?» превращается в «Junior Python разработчик, удалённая работа, Минск». Второе: модель классифицирует сложность запроса, и эта классификация управляет весами ветвей на шаге S2 (адаптивный роутинг из п. 2.3).

Поле `complexity` — не косметика: именно оно позволяет не платить за граф там, где он не нужен, и это прямая реализация рекомендации из обзоров.

### S1a. Лексическая ветвь — BM25 (`pg_textsearch`)

**Решение (Q11):** настоящий **BM25** через расширение `pg_textsearch` (Tiger Data, v1.3.0 production-ready, PostgreSQL 17–18), а не встроенный `ts_rank_cd`. BM25 — каноническая метрика IR, стандарт для гибридного поиска в 2026; в тексте курсовой можно ссылаться на Robertson–Walker и современные hybrid-RAG обзоры.

Индекс BM25 по полю `search_vector` (title A, skills B, company C, description D). Конфигурация FTS выбирается по `vacancies.language` (`russian` / `english`).

**Дополнительно (Q12):** реализуем **вторую лексическую ветвь** — sparse-режим BGE-M3 (lexical weights той же модели). В продакшн-пайплайне основная лексическая ветвь — BM25; sparse BGE-M3 участвует в абляциях (сравнение «BM25 vs sparse BGE-M3 vs обе»).

Ветвь нужна для точных терминов: «1С:Предприятие 8.3», «ГОСТ 34», «k8s», редкие аббревиатуры — то, что плотный поиск пропускает.

### S1b. Плотная ветвь

Модель энкодера — см. раздел 4. Индекс — HNSW по косинусу:

```sql
CREATE INDEX idx_vacancies_embedding_hnsw
  ON vacancies USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

Два принципиальных исправления относительно 2026:

1. **Симметрия кодирования.** И вакансия, и запрос кодируются одной и той же инструкцией/шаблоном. Современные энкодеры (E5, BGE, Qwen3) instruction-aware и требуют разных префиксов для запроса и документа — это не «асимметрия», а документированный контракт модели, в отличие от самодельного взвешенного повторения полей.
2. **Чанкинг.** Вместо одного вектора на вакансию — вектор документа (title + структурные поля + сжатая выжимка) плюс векторы чанков описания. Поиск идёт по чанкам, агрегация до вакансии через max-pooling. Это чинит потерю длинных описаний.

### S1c. Графовая ветвь

Граф навыков и профессий (модель данных — [04-data-model.md](04-data-model.md)):

**Узлы:** `Vacancy`, `Company`, `Skill`, `Occupation`, `Industry`, `Location`.

**Рёбра:**

| Ребро | Смысл | Источник |
|---|---|---|
| `Vacancy —REQUIRES→ Skill` | вакансия требует навык, с весом важности | извлечение из описания |
| `Skill —ALTERNATIVE_OF→ Skill` | синонимы и варианты написания («k8s» ↔ «Kubernetes») | таксономия + словарь |
| `Skill —BROADER/NARROWER→ Skill` | иерархия («React» ⊂ «JavaScript-фреймворки») | таксономия |
| `Skill —RELATED_TO→ Skill` | ассоциация, вес по co-occurrence в корпусе | статистика корпуса |
| `Occupation —TYPICALLY_REQUIRES→ Skill` | типичный профиль профессии | таксономия + агрегация |
| `Occupation —TRANSITIONS_TO→ Occupation` | карьерный переход | таксономия + агрегация |
| `Vacancy —POSTED_BY→ Company`, `—LOCATED_IN→ Location` | атрибутивные связи | нормализация |

**Алгоритм ветви:**

1. Навыки из `SearchIntent` линкуются к узлам `Skill` (точное совпадение → синоним → нечёткое по `pg_trgm` → векторное по эмбеддингу навыка).
2. Расширение на 1–2 хопа по `ALTERNATIVE_OF` (вес 1.0), `NARROWER` (0.8), `RELATED_TO` (вес ребра × 0.6). Затухание с расстоянием.
3. Сбор вакансий, требующих любой из расширенных навыков.
4. Скоринг: взвешенное покрытие навыков — сумма весов совпавших навыков, нормированная на сумму весов требуемых, с учётом важности навыка в вакансии и IDF навыка по корпусу (редкий навык весит больше).

Реализуется рекурсивным CTE в PostgreSQL. Ограничения: максимум 2 хопа, максимум 200 узлов в расширенном множестве, отсечение по порогу веса — иначе граф «расползается» и приносит шум (та самая проблема из п. 2.1).

**Почему не Neo4j.** JobMatchAI использует Neo4j, но у нас граф маленький (десятки тысяч узлов, сотни тысяч рёбер) и обходы неглубокие (≤ 2 хопа). Рекурсивный CTE в PostgreSQL справляется за единицы миллисекунд, а отдельная графовая СУБД добавила бы: второе хранилище, синхронизацию между БД (классический источник рассинхрона), ещё один контейнер, ещё один язык запросов. Для курсовой это чистый оверхед. В «направлениях развития» можно честно написать, что при росте до миллионов узлов и глубоких обходов переход на Apache AGE или Neo4j оправдан.

### S2. Слияние — Reciprocal Rank Fusion

```
score(d) = Σ_branch  w_branch / (k + rank_branch(d)),   k = 60
```

RRF выбран потому, что BM25-скор не ограничен сверху, косинусное расстояние лежит в [0, 2], а покрытие навыков — в [0, 1]. Складывать их напрямую некорректно; RRF использует только позиции в ранжировании и снимает проблему нормализации. Значение k = 60 — из оригинальной работы Cormack et al., но трактуем его как настраиваемый гиперпараметр и подбираем на размеченном наборе.

Веса ветвей адаптивны по `complexity`:

| complexity | w_lexical | w_dense | w_graph |
|---|---|---|---|
| `SIMPLE` | 0.4 | 0.5 | 0.1 |
| `MODERATE` | 0.3 | 0.4 | 0.3 |
| `COMPLEX` | 0.2 | 0.35 | 0.45 |
| `EXPLORATORY` | 0.1 | 0.3 | 0.6 |

Значения — стартовые, подбираются на валидационном наборе. Сама таблица — отличный материал для главы 4 (показать, как меняется nDCG при разных весах).

### S3. Ограничения и релаксация

Жёсткие ограничения применяются как SQL-предикаты **внутри каждой ветви** (важно: в pgvector фильтрация после приближённого сканирования HNSW может «съесть» кандидатов, поэтому включаем iterative scans, `hnsw.max_scan_tuples`).

Релаксация — улучшенная версия механизма 2026 года:

- порог `minCandidates` поднят с 1 до разумного (20), иначе релаксация никогда не срабатывает;
- ограничения снимаются не «целым полем», а по возрастанию веса из `softConstraints`;
- `hardConstraints` не снимаются никогда (в 2026 «защищённые» ключи снимались последними, но всё же снимались);
- **шаги релаксации возвращаются в API и показываются пользователю**: «по удалёнке ничего не нашлось, показываю гибрид». В 2026 эта диагностика считалась, но выбрасывалась.

### S4. Реранкинг cross-encoder

Cross-encoder читает пару (запрос, вакансия) совместно и потому заметно точнее bi-encoder'а; он слишком медленный для полного корпуса, но применяется только к top-50 после фузии. Это стандартная каскадная схема.

Кандидаты моделей — раздел 4. Выход: top-10 с калиброванным скором.

Реранкинг — управляемый тумблер: при недоступности реранкера система отдаёт RRF-порядок (graceful degradation), а в главе 4 сравниваются оба режима.

### S5. Персонализация

Мягкие корректировки поверх скора реранкера:

- совпадение с навыками профиля пользователя (из `user_profile_skills`);
- близость к ранее добавленному в избранное (центроид эмбеддингов избранного);
- негативный сигнал: явно скрытые/отклонённые вакансии;
- ограничения из долговременной памяти (например, «только Гродно»).

Персонализация ограничена по влиянию (не более ±15% скора), чтобы не создавать «пузырь» и не ломать воспроизводимость экспериментов. Для оценки в главе 4 отключается.

### S6. Объяснимость

Главная продуктовая и научная фича. Для каждой вакансии считается разложение (подход JobMatchAI — «белый ящик»):

```ts
interface MatchExplanation {
  totalScore: number;             // 0..100
  factors: {
    skillFit: FactorScore;        // покрытие навыков
    semanticFit: FactorScore;     // близость эмбеддингов
    lexicalFit: FactorScore;      // совпадение терминов
    experienceFit: FactorScore;   // соответствие грейда
    formatFit: FactorScore;       // формат/график/занятость
    salaryFit: FactorScore;       // зарплатные ожидания
  };
  matchedSkills: SkillMatch[];    // совпало напрямую или через синоним
  relatedSkills: SkillMatch[];    // совпало через граф, с указанием пути
  missingSkills: SkillMatch[];    // требуется, но нет у пользователя
  retrievedBy: RetrievalBranch[]; // какие ветви нашли эту вакансию
}
```

Скор детерминированный, считается кодом, а не LLM. LLM только пересказывает его человеческим языком. Это критично: объяснение, сгенерированное моделью «из головы», — это галлюцинация, а не объяснение.

Поле `relatedSkills` с путём в графе («Docker → RELATED_TO → Kubernetes») — прямая демонстрация пользы графовой ветви, и на защите это показывается одним скриншотом.

- **CUDA недоступна** — GPU не AMD-совместимой экосистемы для PyTorch на macOS нет;
- **PyTorch MPS недоступен** — бэкенд MPS поддерживается только на Apple Silicon, на Intel-маках с Radeon его нет;
- **все инференсы — только на CPU**, AVX2 есть, AVX-512 нет;
- 32 ГБ RAM — не ограничение, модели такого размера помещаются свободно;
- Docker работает нативно на x86_64, без эмуляции — накладных расходов на трансляцию нет.

Практический вывод: **офлайн-индексация может быть медленной (это разовая ночная задача).** Latency на CPU не выбирает реранкер: прод — `bge-reranker-v2-m3` (ADR-022). Строки ниже — оценка, в том числе лёгкой модели для абляции.

Оценка пропускной способности на этом CPU (ONNX Runtime, квантование INT8):

| Операция | Модель | Оценка |
|---|---|---|
| Кодирование короткого запроса (~32 токена) | BGE-M3 (568M) | 50–100 мс |
| Кодирование документа (512 токенов) | BGE-M3 (568M) | 60–120 мс/шт, батчами 8–15/с |
| Реранк пары (512 токенов) | bge-reranker-v2-m3 (568M) | ~100 мс/пара → **top-50 ≈ 5 с** |
| Реранк пары (256 токенов) | лёгкий reranker ~278M (абляция) | ~25 мс/пара → **top-20 ≈ 0.5 с** |

Оценка top-50 для `bge-reranker-v2-m3` — около 5 секунд, замер top-20 — около 6.5 секунд. Это принятый прод (ADR-022), не повод менять модель на более слабую. Строка ~278M — абляция.

### 4.1 Энкодер (bi-encoder)

| Модель | Параметры | Размерность | Контекст | MMTEB | Скорость на CPU |
|---|---|---|---|---|---|
| `paraphrase-multilingual-MiniLM-L12-v2` | 118M | 384 | 512 | — | очень быстро; базовая линия 2026, устарела |
| `intfloat/multilingual-e5-small` | 118M | 384 | 512 | ~57 | очень быстро |
| `intfloat/multilingual-e5-base` | 278M | 768 | 512 | ~60 | быстро |
| **`BAAI/bge-m3`** | **568M** | **1024** | **8192** | **59.56** | **приемлемо (офлайн)** |
| `intfloat/multilingual-e5-large-instruct` | 560M | 1024 | 512 | 63.22 | как BGE-M3 |
| `Qwen3-Embedding-0.6B` | 600M | 1024 (MRL) | 32K | 64.23 | как BGE-M3 |
| `Qwen3-Embedding-4B/8B` | 4–8B | 2560/4096 | 32K | до 70.58 | нереалистично на этом CPU |

**Решение: `BAAI/bge-m3`.**

Аргументы:
- на ruMTEB лидирует именно в категории Retrieval среди non-instruct моделей — а наша задача ровно retrieval;
- **корпус двуязычный.** rabota.by, ГСЗ, praca.by и Хабр Карьера — русский; LinkedIn и Indeed — английский. BGE-M3 обучен именно на кросс-язычный поиск (100+ языков), что позволяет русским запросом находить англоязычные вакансии без машинного перевода. Для E5-моделей это тоже работает, но у BGE-M3 это заявленная сильная сторона;
- контекст 8192 покрывает описание вакансии целиком;
- умеет выдавать dense, sparse (lexical weights) и multi-vector одной моделью — то есть лексическую ветвь можно построить и на нём тоже, и сравнить с Postgres FTS (вопрос Q12);
- MIT-лицензия;
- inference на запросе — одна короткая строка, 50–100 мс, в бюджет укладывается.

Индексация тяжёлая, но разовая: 15 000 вакансий × примерно 4 представления (документ + чанки) = 60 000 эмбеддингов, при 10/с это около **1.7 часа**. Запускается на ночь. Важное следствие: **каждая смена модели энкодера в абляциях стоит ещё одного такого прогона**, поэтому в главе 4 сравниваем не больше двух энкодеров.

**Базовая линия для сравнения:** `paraphrase-multilingual-MiniLM-L12-v2` (модель курсовой 2026) — она лёгкая, её переиндексация стоит минут двадцать, и это даёт прямое численное сравнение «прошлая работа против текущей».

### 4.2 Реранкер (cross-encoder)

| Модель | Параметры | top-20 @ 256 ток. на CPU | Комментарий |
|---|---|---|---|
| **`BAAI/bge-reranker-v2-m3`** | **568M** | **~6.5 с на замере top-20** | **prod (ADR-022)** |
| `Qwen3-Reranker-0.6B` | 600M | ~2 с | не выбран |
| `jina-reranker-v2-base-multilingual` | 278M | ~0.5 с | абляция |
| `BAAI/bge-reranker-base` | 278M | ~0.5 с | абляция |

**Решение (ADR-022): `BAAI/bge-reranker-v2-m3` (568M)** — prod reranker, top-20 (top-50 в абляциях), TEI CPU/ONNX. Замер i9-9880H: **~6.5 s** top-20 — приемлемо; latency обосновывается железом.

Лёгкие reranker'ы (~278M) — абляции и деградация (~2 s). Rerank отключаем; строка «без rerank» в таблице абляций.

### 4.3 Где запускать

**Решение: контейнер Hugging Face Text Embeddings Inference (TEI), CPU-образ, модели в формате ONNX с INT8-квантованием.** Поднимает и энкодер, и реранкер по HTTP (`/embed`, `/rerank`), даёт батчинг из коробки, не требует ни строчки Python.

Запасной вариант, если TEI на Intel-маке окажется капризным: **Transformers.js v3** (`@huggingface/transformers`) — запускает те же ONNX-модели прямо в Node через ONNX Runtime. Медленнее TEI, но убирает целый контейнер и оставляет стек полностью на TypeScript. Проверяется на первой неделе разработки.

### 4.4 Генеративная LLM

**Решение (Q27): OpenRouter** — единственный провайдер на dev и prod. Google AI Studio недоступен (регион). GPT-4o / отдельный DeepSeek — не приоритет; платные модели на OpenRouter с `json_schema` предпочтительнее.

| Задача | Требования | Провайдер |
|---|---|---|
| `understand` | строгий `json_schema` | OpenRouter — модель с structured output (**даже платная**) |
| `generate` | качество текста, стриминг | OpenRouter |
| `extract-skills` | дёшево, объём большой | OpenRouter, батчи, кэш по `content_hash` |
| `summarize-chat`, `extract-memory` | дёшево | OpenRouter |
| `parse-resume` | structured output | OpenRouter |

**Практика:** `extract-skills` на dev — подвыборка 500–1000 вакансий; полный прогон — один раз перед финальными замерами. Кэш LLM в Redis. Бенчмарк: `SearchIntent` кэшируется на диск.

## 5. Извлечение и нормализация навыков

Без этого шага граф не построится. Пайплайн на стороне `ingestion-service`:

1. **Извлечение.** LLM читает описание вакансии и возвращает список навыков с типом (`hard` / `soft` / `tool` / `language`), важностью (`required` / `preferred`) и цитатой-обоснованием из текста. Structured output, батчинг, кэш по `content_hash`.
2. **Нормализация к канону.** Каскад: точное совпадение → таблица синонимов → нечёткое совпадение `pg_trgm` (порог 0.8) → векторное сопоставление по эмбеддингу названия навыка (порог 0.85) → создание нового узла-кандидата с флагом `needs_review`.
3. **Пополнение графа.** Рёбра `REQUIRES` с весами; пересчёт `RELATED_TO` по co-occurrence (PMI или Jaccard) раз в сутки; пересчёт IDF навыков.

### Про таксономию

JobMatchAI и работа по multilingual skill extraction опираются на **ESCO** (European Skills, Competences, Qualifications and Occupations) — ~13 900 навыков, ~3 000 профессий, иерархия и связи, официально многоязычная. Проблема: **русского языка в ESCO нет**.

Варианты (вопрос Q5):

| Вариант | Плюсы | Минусы |
|---|---|---|
| ESCO + машинный перевод меток на русский | стандартизованная иерархия «из коробки», ссылка на признанную таксономию, сравнимость с литературой | качество перевода ИТ-терминов, размер |
| Таксономия, построенная из корпуса (bottom-up): извлечь навыки, кластеризовать, связать LLM | точно соответствует белорусскому рынку, полностью наша разработка → сильный элемент новизны | больше работы, нет внешней валидации |
| Гибрид: скелет ESCO (верхние уровни) + листья из корпуса | лучшее из двух | самый трудоёмкий |

Моё предложение — **гибрид**, но урезанный: берём из ESCO только группы профессий и верхние 2–3 уровня иерархии навыков (их немного, перевести/сверить реально вручную), а конкретные навыки набираем из корпуса и привязываем к этим группам. Это и ссылка на стандарт, и собственная работа.

## 6a. Ограничения исследования

Раздел, который обязательно должен быть в работе — он снимает половину вопросов комиссии:

1. **Реранкер выбран по качеству (ADR-022).** На CPU `bge-reranker-v2-m3` занимает несколько секунд на top-20. Это ограничение железа. Модель ~278M в прод не ставится: она нужна только строке абляции. На GPU тот же пайплайн был бы заметно быстрее.
2. **Число сравниваемых энкодеров ограничено двумя** — каждая переиндексация корпуса занимает часы.
3. **Размер бенчмарка** ограничен трудоёмкостью ручной разметки (см. [08-evaluation.md](08-evaluation.md)).
4. **Корпус географически и отраслево смещён** в сторону ИТ (Хабр Карьера, dev-сегмент LinkedIn) и крупных городов.
5. **Оценка проводится на статическом снимке корпуса**, тогда как в реальной эксплуатации база меняется ежедневно.
