# TEI в Docker: всегда или по желанию

**Решение (2026-10-11): позиция B.** Оба контейнера входят в обычный `docker compose up`. Профиля нет. Запись — [ADR-033](../Wiki/10-decision-log.md). Ниже — две формулировки, из которых выбирали.

## Позиция A. Контейнеры необязательны

Источник: `Wiki/progress-log.md`, этап 6, слова «TEI Docker — опционально».

Смысл: обычный `docker compose up` поднимает Postgres, Redis, core-api, llm-service, ingestion и web. Два контейнера с нейросетями не стартуют, веса не скачиваются, память под них не занимается.

Как это выглядит на практике:

```bash
docker compose up
# postgres, redis, api, llm, ingestion, web — да
# tei и tei-rerank — нет

docker compose --profile tei up
# то же самое плюс BGE-M3 и bge-reranker-v2-m3
```

Зачем так: первая загрузка `BAAI/bge-m3` и `BAAI/bge-reranker-v2-m3` — это гигабайты и минуты, на машине без GPU оба процесса сидят в RAM. Пока идёт работа над логином или чатом, энкодер не нужен. Ingestion этапа 7 тоже не вызывает `/embed`: вектор пишется на этапе 8.

Что придётся поменять, если выбрать это:

- В `docker-compose.yml` у `tei` и `tei-rerank` появляется `profiles: [tei]`.
- `retrieval-service` больше не может безусловно зависеть от них. Сейчас пустой `TEI_EMBED_URL` в пробе readiness считается «сервис лежит» (`buildRetrievalProbes` возвращает `false`). Для опционального режима пустой URL должен значить «поиск без нейросети», а не «сервис сломан».
- `Wiki/01-architecture.md` §6 придётся поправить: там написано, что Compose поднимает `tei` и `tei-rerank` вместе с остальными.

## Позиция B. Контейнеры всегда в стеке

Источник: `Wiki/01-architecture.md` §2.6 и §6. Там embedding-runtime — два контейнера TEI, и `docker compose up` поднимает их рядом с Postgres и Redis.

Смысл: одна команда поднимает ту систему, которая нарисована на схеме. Поиск без энкодера не считается готовым стеком.

Как это выглядит на практике:

```bash
docker compose up
# вместе с api стартуют tei (BAAI/bge-m3) и tei-rerank (BAAI/bge-reranker-v2-m3)
# retrieval ждёт, пока каждый ответит GET /health
```

Первый запуск на чистой машине: образ TEI, затем веса. Healthcheck в этой ветке даёт на это `start_period: 600s` и ещё повторы. Пока `/health` не отвечает, retrieval не стартует. core-api и web от TEI не зависят: логин можно открыть, даже если модели ещё качаются. Но контейнеры уже запущены и уже едят диск и сеть.

Живой вызов `/embed` и `/rerank` в этой ветке не делался. Healthcheck проверяет, что процесс жив, а не то, что вектор 1024-мерный.

## Что выглядит убедительнее

Убедительнее позиция B для описания продукта и позиция A для повседневной разработки. Это не одна настройка.

Продуктовый стек, который показывается на схеме и на защите, включает энкодер и реранкер. Иначе `docker compose up` поднимает не ту систему, которая описана в архитектуре: retrieval сразу будет not ready, потому что его проба ходит на `http://tei:80/health`.

Повседневная разработка логина и ingestion эти две модели не вызывает. Тащить их в каждый `up` дорого: на Intel-ноутбуке из ADR-022 это заметные минуты и гигабайты, на Apple Silicon образ TEI CPU ещё и amd64 через эмуляцию.

## Принято

Позиция B. Контейнеры остаются в обычном `docker compose up`, retrieval ждёт `GET /health`. Профиль из позиции A не делается.
